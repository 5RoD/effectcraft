# Third-party After Effects workflow parity

This note compares the requested plug-ins by the user-visible work they help people do. It uses public vendor descriptions and EffectCraft's public feature documentation only. It does not inspect plug-in binaries, vendor source, or commercial preset data. Product descriptions can change; links below were checked on 8 October 2026.

EffectCraft remains the product name. The requested 5RoD red, white, and cyan palette is a product-design direction, not a request to copy a vendor interface or its artwork. After Effects SDK plug-ins and these commercial products cannot be loaded by EffectCraft. The available extension route is EffectCraft's own sandboxed WebAssembly effect API ([plug-ins](../plugins.md)); matching a workflow means implementing original, interoperable behavior, not claiming compatibility with a vendor's proprietary algorithm or preset library.

## Workflow parity matrix

The matrix records the upstream baseline used for research. This fork subsequently added the
counter, quick-animation and seeded-shake tools described in [native motion tools](../native-motion-tools.md),
plus easing-library import/export and saved branching history described in [development status](README.md).
The remaining vendor-specific workflows and quality acceptance still apply.

The strongest shared need across these products is a fast, reversible workflow: useful actions should be batchable, configurable, deterministic, easy to repeat, and represented as ordinary editable project data. Presets should be original and portable. Any action that changes a project should be a single named command so undo, branching history, automation, and later persistent history can all describe it.

## Persistent history and crash-safe saving

This section records the upstream 0.6.0 baseline, before this fork's history extension and
checkpoint fixes. See [development status](README.md) for implemented changes and remaining limits.

EffectCraft already has a **session-local branching history**: editing after undo preserves the abandoned future as a branch, the History panel can jump to any retained state, and undo is a pointer swap over `Arc<Project>` snapshots. Retention is bounded by the undo-level preference, so this is not an archive of literally every operation. See [`history.rs`](../../crates/engine/src/history.rs), [`Session::apply`](../../crates/engine/src/lib.rs), and the [architecture notes](../architecture.md). This is stronger than a linear undo stack while the process remains open.

That history is not durable yet. Current node IDs are based on an `Arc` address and only stay stable while those snapshots remain alive. The tree itself is not serialized. Opening/replacing a project resets `History`, and the existing rotating `.ecproj` autosaves store project content, not undo/redo/branch history. Autosave runs in the background on desktop and the config layer has a sibling-temp-file, flush, rename atomic-write helper. The crash-recovery sentinel points to a latest project autosave, not the full editing history. Relevant implementation: [`history.rs`](../../crates/engine/src/history.rs), [`autosave.rs`](../../crates/engine/src/autosave.rs), [`config.rs`](../../crates/engine/src/config.rs), [`lib.rs`](../../crates/engine/src/lib.rs).

Recommended design for the requirement “travel through every edit, branch, and reopen”:

1. Give revisions persistent IDs independent of memory addresses. Store a versioned history manifest with project identity, schema/version, root/current/saved revision IDs, operation labels, parent/child edges, branch names/metadata, and checksums. Keep editor-only UI state separate unless explicitly needed to restore a working view.
2. Persist immutable revision snapshots or compact, validated command/diff records in an append-only journal, with periodic full checkpoints. Reuse the existing project snapshot model, sharing/deduplication, `FileOps`, background serializer, and atomic-write path. A journal record must be durable before the UI reports a committed revision as protected; coalesce continuous gestures exactly as the undo system does, so pointer drags do not create unbounded history entries. Checkpointing and replay must stay off the render/UI critical path.
3. Commit data before publishing the manifest pointer: write a checksummed record/temp snapshot, flush it, then atomically replace the manifest. Keep the previous known-good manifest and autosave until the new one verifies. On startup, validate the project and history independently, replay only complete records, and offer the latest valid recovery without discarding branches. A missing, old-version, or corrupt history store must still open the project and report that history recovery was incomplete.
4. Make project save, autosave rotation, save-as, copy/move, and recovery operate on the history store as one logical project package. Preserve branch IDs across save/reopen; imported projects without a matching history begin a new root. Define behavior for cross-volume moves, duplicate project copies, older app versions, low disk space, interrupted writes, and retention limits. Protected/named branches and the current/saved revision must never be pruned silently.
5. Bound disk and reopen cost with user-visible retention settings, content deduplication, checkpoints, background compaction, and corruption diagnostics. Report which old revisions are retained/pruned and never claim “never lose work” until fault-injection tests cover process termination, disk-full/write/rename failure, interrupted compaction, and recovery on each supported filesystem/runtime.

The existing in-memory whole-project snapshots provide constant-time navigation but can retain substantial memory; directly serializing every full snapshot synchronously would create latency and disk growth. A durable hybrid should preserve the familiar snapshot semantics while amortizing serialization and storage, and it must be benchmarked with large projects and long histories before promising “every edit.”

## Acceptance checklist

- [ ] Product wording distinguishes “workflow equivalent” from third-party plug-in compatibility; no vendor code, binary, preset, branded artwork, or proprietary algorithm is copied.
- [ ] Counter workflow: animate one value through fractional, negative, large, countdown, time, symbol, padding, localization, and fixed-width examples; reopened projects render identical strings and stable alignment.
- [ ] Ease workflow: create/edit/capture/apply/save/rename/delete and import/export a curve library; check multi-selection and keyframe value/time edits, curve copy/paste, and portable versioning.
- [ ] Animation actions: apply to one and many layers, test both stagger directions, playhead alignment, configurable easing/overshoot, trim/fade/transform actions, locked-layer behavior, deterministic results, one undo step, and branch recovery.
- [ ] Glow workflow: test HDR/linear and nonlinear inputs, threshold animation flicker, masks, compositing, 3D camera movement, text/shape sources, quality settings, GPU/device-loss fallback, and warm/cold performance at 1080p/4K.
- [ ] Shake workflow: test axes, duration/range, decay, seed determinism, multi-layer application, preset round trip, preview responsiveness, render determinism, and undo/redo.
- [ ] Retiming workflow: compare representative ramp/slow-motion clips containing occlusions, cuts, textureless regions, alpha mattes, 360 seams, variable frame rates, and audio. Track quality and render time separately; label unsupported modes rather than silently approximating them.
- [ ] Durable-history workflow: make edits A→B, undo, create C, save, close/reopen, and verify A/B/C branch traversal and stable revision identity; jump to an old state, save, and verify the saved marker after reopen.
- [ ] Durable-history recovery: kill the process at each journal/checkpoint/manifest boundary; simulate truncation, checksum mismatch, full disk, permission failure, rename failure, stale temp files, and interrupted compaction; always recover the newest complete state and preserve the last good project.
- [ ] Durable-history performance: benchmark command latency, frame/render responsiveness during persistence, memory retention, journal/checkpoint size, startup replay, and compaction on small and large projects. Verify that background work is cancellable and bounded.
